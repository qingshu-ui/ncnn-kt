# ncnn-kt: Kotlin Multiplatform bindings for ncnn

This document describes the design and usage of the ncnn bindings in this repository.
It supersedes the obsolete scratch documents in `tmp/` (in particular the claim there
that cinterop can bind ncnn's C++ headers — Kotlin/Native cinterop only binds C).

## Module layout

| Module | Platform | Responsibility |
|---|---|---|
| `ncnn-binding` | Kotlin/Native | ncnn C API cinterop and the JNI-compliant `@CName("Java_...")` exports. Targets Linux x64, MinGW x64, and Android Native. Builds `libncnn_jni`. |
| `ncnn-jni` | Kotlin/JVM | Declares the external JNI functions and owns the JVM `NativeLoader`. Has no compile dependency on `ncnn-binding`; a Gradle `Copy` task places the binding output and ncnn runtime under `src/main/resources/natives/<platform>`. Android uses its own loader in `ncnn-core`'s `androidMain`. |
| `ncnn-core` | Kotlin Multiplatform | Public API (`Ncnn`, `Mat`, `Net`, `Extractor`, `PixelFormat`, `NcnnException`). JVM/Android use `ncnn-jni`; native targets call `ncnn-binding` cinterop. |
| `ncnn-android-native` | Android AAR | Packages the Android `libncnn_jni.so` and `libncnn.so` produced by `ncnn-binding` into an AAR. It contains no Kotlin or JNI declarations. |

Dependency direction:

```
ncnn-core
  ├─ jvmSharedMain (custom source set shared by jvm + android) ──> ncnn-jni
  └─ nativeMain ────────────────────────────────────────────────> ncnn-binding (cinterop)

ncnn-jni  ──(no compile dependency)──> ncnn-binding build outputs (Gradle Copy only)

android-test-app ──> ncnn-core
                       └─ runtimeOnly: ncnn-android-native (AAR)
                                             └─ dependsOn :ncnn-binding:buildAndroidJni
```

### Why `jvmSharedMain`?

`jvmSharedMain` is **not** a default KMP source set. It is created explicitly in
`ncnn-core/build.gradle.kts`:

```kotlin
val jvmSharedMain = create("jvmSharedMain") {
    dependsOn(commonMain.get())
}
jvmMain.get().dependsOn(jvmSharedMain)
findByName("androidMain")?.dependsOn(jvmSharedMain)
```

It contains the JNI-backed `MatJvm`, `NetJvm`, and `JvmFactories` implementations shared
by the JVM and Android targets, avoiding a second copy of those files. It also declares
`internal expect fun loadNativeLibrary()`; `jvmMain` delegates to `ncnn-jni`'s
`NativeLoader`, while `androidMain` loads `libncnn.so` and then `libncnn_jni.so` through
`System.loadLibrary`.

## ncnn SDK

`buildSrc` has been removed. The build no longer downloads or prepares ncnn itself.
Instead, a repo-local SDK is used:

```
third_party/ncnn/
  include/ncnn/{c_api.h, platform.h, ncnn_export.h}   # committed
  windows-x64/{bin/ncnn.dll, lib/ncnn.lib}            # fetched, gitignored
  linux-x64/lib/libncnn.so*                           # fetched, gitignored
  android/<abi>/lib/libncnn.so                        # fetched, gitignored
```

- `c_api.h` is copied from the ncnn source at the pinned tag `20261020`.
- `platform.h` and `ncnn_export.h` are committed portable headers. They mirror the
  feature switches used by the official prebuilt packages and avoid host-specific
  generated headers.
- The prebuilt libraries are fetched by `scripts/fetch-ncnn-release.ps1` (Windows) and
  `scripts/fetch-ncnn-release.sh` (Linux). Both verify the release SHA-256 before
  extraction and then normalize the release layout into the directories above.

See [`third_party/ncnn/README.md`](../third_party/ncnn/README.md) for the pinned asset
table, SHA-256 values, and upgrade steps.

## Cinterop definitions

The cinterop inputs are explicit committed files, not generated by Gradle:

`ncnn-binding/src/nativeInterop/cinterop/ncnn.def`:

```properties
headers = ncnn/c_api.h
headerFilter = ncnn/c_api.h ncnn/platform.h ncnn/ncnn_export.h
package = ncnn
```

`../ncnn-jvm-jni/src/nativeInterop`:

```properties
headers = jni.h
headerFilter = jni.h jni_md.h
package = jni
```

The build script passes the include directories (`third_party/ncnn/include` and the JDK
`include` directory) and the platform library paths, because those depend on the local
checkout. The `.def` files describe the bindings themselves.

## Version pinning

- ncnn: **20261020**, consumed from Tencent's official prebuilt release packages. Each
  package is pinned by SHA-256 in the fetch scripts and in `third_party/ncnn/README.md`.
- Kotlin: **2.3.21**, Gradle: **9.4.0**, AGP: **9.0.0**, JDK: **21**.
- Android: Android SDK `platforms;android-37.0` / `build-tools;37.0.0`; the Kotlin/Native
  Android targets provide their own NDK toolchain.

No ncnn sources are compiled. The release libraries are fetched explicitly into
`third_party/ncnn/`; the build has no network access of its own.

## What is bound

Both backends call ncnn's **C API** (`c_api.h` from the committed SDK headers), which
covers everything exposed here:

| Kotlin | ncnn C API |
|---|---|
| `Ncnn.version` / `Ncnn.versionNumber` | `ncnn_version`, `ncnn_version_number` |
| `Net`, `Extractor`, `Mat` | `ncnn_net_*`, `ncnn_extractor_*`, `ncnn_mat_*` |
| `Net` option properties | `ncnn_option_get_*` / `ncnn_option_set_*` |
| Pixel conversion / resize | `ncnn_mat_from_pixels*`, `ncnn_mat_to_pixels*` |
| Packing / flatten / normalize | `ncnn_convert_packing`, `ncnn_flatten`, `ncnn_mat_substract_mean_normalize` |

Backends:

- **JVM**: `ncnn-binding` builds a Kotlin/Native `sharedLib` that exports the JNI entry
  points with `@CName("Java_io_github_qingshu_ncnn_NcnnJni_...")` and calls ncnn through
  cinterop. `ncnn-jni` declares the matching external functions and loads the library.
- **Android**: Kotlin/Native Android shared libraries using the same `@CName` exports;
  JNI types come from the `platform.android` bindings. `ncnn-android-native` packages the
  ABI libraries into an AAR. `ncnn-core`'s `androidMain` loads `libncnn.so` first and then
  `libncnn_jni.so` from the APK's native library directory.
- **Kotlin/Native**: `ncnn-core`'s `nativeMain` calls the cinterop declarations from
  `ncnn-binding` directly.

Layers are not bound individually. Layer functionality is reached by loading ncnn
`.param` / `.bin` models.

## Platform support

| Platform | Target | Backend | Status |
|---|---|---|---|
| JVM on Windows x64 | `jvm` | JNI from `mingwX64` sharedLib | built and tested locally + CI |
| JVM on Linux x64 | `jvm` | JNI from `linuxX64` sharedLib | CI |
| Windows x64 native | `mingwX64` | cinterop | built and tested locally + CI |
| Linux x64 native | `linuxX64` | cinterop | CI |
| Android `arm64-v8a`, `armeabi-v7a`, `x86_64` | `android` | JNI from `androidNative*` sharedLibs in an AAR | built locally + CI |

Not supported in this version:

- **macOS and iOS**: the binding scope is Linux, MinGW, and Android Native. The JVM
  desktop build has no macOS JNI library. macOS/iOS targets are not declared.
- **Linux arm64**: Tencent publishes no Linux arm64 prebuilt release, so it would be a
  link-disabled target only.
- **Vulkan / GPU**: the Kotlin API does not expose Vulkan options or GPU execution.
- **Batch inference**: `Mat.n` is exposed read-only, but batch construction is not.
- **WebAssembly / JS**, **HarmonyOS**, **Windows arm64/x86**, **Linux riscv64**.
- **Publishing/signing** to Maven Central is not configured.

Desktop Kotlin/Native targets are declared unconditionally so IDE indexing works. Cinterop
for the non-host desktop target is generated from the committed headers; linking and test
execution are disabled for non-host targets. KGP cross-compiles cinterop as an **unpacked**
klib, while the IDE's Gradle model points at the packed `build/libs/*.klib`; a
`packCinteropKlib<target>` task still writes the packed klib for IDE resolution.

## Build prerequisites

| Host | Required |
|---|---|
| Windows | JDK 21, the Kotlin/Native toolchain (downloaded by Gradle), and the Windows ncnn SDK from the fetch script |
| Linux | JDK 21, the Kotlin/Native toolchain, and the Linux ncnn SDK from the fetch script |
| Android | Android SDK with `platforms;android-37.0` and `build-tools;37.0.0`. The Kotlin/Native Android targets download their own NDK toolchain; a local NDK is not required. |

No CMake, Ninja or C/C++ compiler is needed for the JNI libraries: `ncnn-binding` builds
them as Kotlin/Native shared libraries.

### Fetch the ncnn SDK

```powershell
# Windows
pwsh ./scripts/fetch-ncnn-release.ps1 -Platform windows-x64
```

```bash
# Linux
bash ./scripts/fetch-ncnn-release.sh --platform linux-x64

# Android (also needs linux-x64 for the host ncnn-jni resources)
```

- `-Pncnn.android=true|false` — enable/disable the Android target and modules (default `true`).
- `-Pncnn.android.abis=arm64-v8a,armeabi-v7a,x86_64` — Android ABI subset.

## Usage

Public API package and names are unchanged:

```kotlin
import io.github.qingshu.ncnn.*

Net.create().use { net ->
    net.numThreads = 4
    net.loadParam("model.param")
    net.loadModel("model.bin")

    val input = Mat.fromPixels(rgbBytes, PixelFormat.RGB, width = 224, height = 224)
    try {
        val extractor = net.createExtractor()
        val output = try {
            extractor.input("data", input)
            extractor.extract("output")
        } finally {
            extractor.close()
        }
        output.use {
            val floats = it.readFloats()   // fp32 pack1
            // ...
        }
    } finally {
        input.close()
    }
}
```

`Mat.fromPixels(pixels, from, to, ...)` performs an ncnn pixel conversion while building
the tensor; `Mat.toPixels(format)` and `toPixelsResize(format, w, h)` convert back.
`substractMeanNormalize(mean, norm)` applies the usual ncnn normalization.

Consumers depend on `ncnn-core`. The JVM path also needs `ncnn-jni` at runtime; it is an
implementation dependency of `ncnn-core`, so Gradle resolves it automatically when the
project is consumed as a project dependency. The bundled natives live in the
`ncnn-jni` jar, not the `ncnn-core` jar.

## Ownership and lifetime

- Every `Mat`, `Net` and `Extractor` owns a native handle and implements `AutoCloseable`.
  Use `use {}` or `close()`; `close()` is idempotent.
- `Mat.reshape`, `clone`, `convertPacking` and `flatten` return **new** tensors that must be
  closed separately. `reshape`, `convertPacking` and `flatten` share data with the source.
- `Extractor.input(name, mat)` copies a reference-counted tensor header, so the input `Mat`
  may be closed immediately after `input`.
- `Net.close()` closes all extractors that are still open; using an extractor after its net
  was closed throws `IllegalStateException`.
- `Net.clear()` throws if extractors are still open.
- `Net` and `Extractor` are **not thread-safe**. Do not share them between threads. Create
  one extractor per thread (and a net per thread for fully independent execution).

## Errors

- ncnn failures surface as `NcnnException(message, code)`. `code` is the ncnn status
  (usually `-1`, or `-100` for allocation/layer failures).
- `loadModel(memory)` returning 0 for a non-empty model blob is treated as a failure.
- Invalid arguments throw `IllegalArgumentException`; closed handles throw
  `IllegalStateException`; allocation failures throw `OutOfMemoryError` where ncnn reports
  them.
- `readFloats` / `writeFloats` require fp32 pack1 data. Extractor outputs are unpacked to
  pack1 by ncnn; for custom tensors use `convertPacking(1)` (and disable fp16/bf16 storage
  when running on ARM).

The JNI boundary in `ncnn-binding` throws `NcnnBindingException` internally and translates
it to the JVM `io.github.qingshu.ncnn.NcnnException` with the same message/code contract.

## Native library layout

`ncnn-binding` consumes the local `third_party/ncnn` SDK:

| Platform | Link artifact | Runtime artifact |
|---|---|---|
| Windows x64 | `windows-x64/lib/ncnn.lib` | `windows-x64/bin/ncnn.dll` + VC++ runtime DLLs |
| Linux x64 | `linux-x64/lib/libncnn.so` | `linux-x64/lib/libncnn.so*` |
| Android | `android/<abi>/lib/libncnn.so` | same |

`ncnn-binding` builds `libncnn_jni` / `ncnn_jni.dll` for the host desktop target and for
each configured Android ABI. `ncnn-jni` copies the host JNI library plus its ncnn runtime
into `ncnn-jni/src/main/resources/natives/<platform>/`; that generated directory is
gitignored.

### Native loading per platform

The JVM and Android loading paths are deliberately different:

- **JVM**: `ncnn-core`'s `jvmMain` actual calls `ncnn-jni`'s `NativeLoader`. Resolution
  order:
  1. `-Dncnn.jni.path=<library>`
  2. `NCNN_JNI_PATH`
  3. `System.loadLibrary("ncnn_jni")` from `java.library.path`
  4. bundled resource under `/natives/windows-x64` or `/natives/linux-x64`

  On Windows the bundled VC++ runtime and `ncnn.dll` are preloaded; on Linux
  `libncnn.so.1` is preloaded before `libncnn_jni.so`.

- **Android**: `ncnn-core`'s `androidMain` actual loads the AAR libraries from the app's
  native library directory in dependency order:

  ```kotlin
  System.loadLibrary("ncnn")      // libncnn.so
  System.loadLibrary("ncnn_jni")  // libncnn_jni.so
  ```

  `ncnn-android-native` packages `libncnn_jni.so` and `libncnn.so` per ABI.

`ncnn-jni` also carries the desktop natives in its jar, so Android apps should exclude
`natives/**` from packaging (the test app does).

The 49 JNI exports and their helpers live in one shared directory,
`ncnn-binding/src/jniMain/kotlin/`. Only the JNI type aliases differ per platform:

- `ncnn-binding/src/jniDesktop/kotlin/JniTypes.kt` — aliases to the `jni` cinterop over the
  JDK `jni.h`; wired into the host desktop source set.
- `ncnn-binding/src/jniAndroid/kotlin/JniTypes.kt` — aliases to the `platform.android` JNI
  bindings; wired into every Android Native target.

The shared directory is added to the host desktop source set and to each Android Native
target's main source set, together with the matching alias directory.

## Tests

`ncnn-core/src/commonTest` runs on every JVM and native target:

- version, Mat create/fill/clone/reshape/read/write, close semantics;
- pixel round-trip, RGB→GRAY conversion, resize, mean/normalize;
- end-to-end inference from memory with a generated `Input → Convolution(1×1, weight 2) →
  ReLU` network (`[-1, 2, -3, 4]` → `[0, 4, 0, 8]`);
- error paths for missing files and invalid param bytes.

The JVM and native suites additionally load files from temporary paths (the JVM test also
uses a non-ASCII file name to exercise the Windows `_w` path conversion). The Android
instrumentation test in `android-test-app` can run the same inference through the AAR on an
x86_64 emulator (not part of CI; Android CI only compiles the AAR and test app).

Commands:

```bash
# Windows
./gradlew.bat :ncnn-core:jvmTest :ncnn-core:mingwX64Test

# Linux
./gradlew :ncnn-core:jvmTest :ncnn-core:linuxX64Test

# Android compile/AAR
./gradlew :ncnn-core:compileAndroidMain
./gradlew :ncnn-android-native:assembleDebug :android-test-app:assembleDebug

# Formatting
./gradlew spotlessCheck
```

## Upgrading ncnn

1. Update `VERSION` / `$Version` and the release asset names/SHA-256 values in
   `scripts/fetch-ncnn-release.sh`, `scripts/fetch-ncnn-release.ps1`, and
   `third_party/ncnn/README.md`.
2. Refresh `third_party/ncnn/include/ncnn/c_api.h` from the same ncnn source tag
   (`--refresh-headers` / `-RefreshHeaders`) and reconcile `platform.h` /
   `ncnn_export.h` if the upstream feature switches changed.
3. Merge any new C API declarations needed into
   `ncnn-binding/src/jniMain/kotlin/NcnnJniExports.kt` and the native wrappers.
   The platform alias files only change if a JNI type is added.
4. Run the fetch scripts and the CI matrix.

## Continuous integration

`.github/workflows/ci.yml` runs:

- Windows x64: `:ncnn-core:jvmTest :ncnn-core:mingwX64Test :ncnn-jni:jar`
- Linux x64: `:ncnn-core:jvmTest :ncnn-core:linuxX64Test`
- Android: `:ncnn-android-native:assembleDebug :android-test-app:assembleDebug`
- `spotlessCheck`

Each native job runs the corresponding `scripts/fetch-ncnn-release` command before
Gradle. The fetched SDK directories and downloaded archives are cached by the workflow.
No CMake, Ninja or local NDK installation is required; the Kotlin/Native distributions
provide the native toolchains.
